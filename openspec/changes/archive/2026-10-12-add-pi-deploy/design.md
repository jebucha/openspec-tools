# Design

## Context

deploy.sh supports four deploy targets (opencode, kiro, claude, qwen), each with a `deploy_<env>()` function, a force flag, a directory auto-detection line, a dispatch branch, and error-message entries. Three of the four are plain copies (opencode, qwen, and claude's skills); kiro renames commands to `.prompt.md` and claude splits the `opsx-` prefix into a subdirectory. See proposal.md for motivation.

pi (the pi coding agent) uses a `.pi/` directory with two conventions that both match existing source files as-is:
- Commands: `.pi/prompts/<name>.md` — plain markdown prompt templates with YAML frontmatter (`description`); the filename becomes the `/command` name.
- Skills: `.pi/skills/<name>/SKILL.md` — the Agent Skills format (`name`, `description`, `license`, `compatibility`, `metadata` frontmatter), identical to the existing `skills/*/SKILL.md` files.

The repo itself is a pi project: it contains an untracked `.pi/` directory with core workflow files generated by `openspec init` (prompts: `opsx-apply`, `opsx-archive`, `opsx-explore`, `opsx-propose`, `opsx-sync`; skills: `openspec-apply-change`, `openspec-archive-change`, `openspec-explore`, `openspec-propose`, `openspec-sync-specs`), sitting alongside the gitignored `.opencode/` and `.claude/` directories.

## Goals / Non-Goals

**Goals:**
- Make `pi` a first-class deploy target with the same UX as the existing four (auto-detect, force flag, progress output)
- Keep the change minimal and mechanical — no restructuring of deploy.sh beyond adding the fifth target
- Verify byte-identical deployment end-to-end in this repo, which already has a `.pi/` directory

**Non-Goals:**
- No changes to command/skill *content* (frontmatter, wording) — pi's formats are compatible as-is
- No changes to how `openspec init` generates core workflow files for pi
- No changes to `install.sh` (it copies only non-hidden entries, so deploy targets never flow through it)
- No restructuring of the per-target function pattern in deploy.sh
- No cleanup/merge of pre-existing `.pi/` content — deploy.sh never manages prior deployments for any target

## Decisions

**1. `deploy_pi()` copies as-is, mirroring `deploy_qwen()`**

Commands: `commands/*.md` → `.pi/prompts/<name>.md`, preserving the original filename including the `opsx-` prefix. Skills: `skills/*/` → `.pi/skills/*/` unchanged. Progress lines follow the existing format: `  [pi] command: <name>.md` / `  [pi] skill: <name>`.

Evidence: pi prompt templates are plain markdown with `description:` frontmatter and `$@` argument substitution, and pi's skill frontmatter fields are a superset-compatible match for the existing `SKILL.md` files (verified against pi 1.1.0 docs). No conversion is needed — unlike gemini's historical TOML conversion.

Alternatives considered:
- Converting to a pi-specific format — rejected; pi accepts the existing markdown/SKILL.md formats as-is
- Reusing `deploy_qwen()` with a parameter — rejected; the existing per-target function pattern is the repo convention, and a parameterized function would be a refactor beyond this change's scope

**2. Target directory is `.pi/prompts/`, not `.pi/commands/`**

pi calls its prompt templates "prompts" and derives the slash-command name from the filename. The repo's own `.pi/prompts/` (containing `opsx-apply.md`, `opsx-explore.md`, etc.) confirms the layout. This is the one structural difference from `deploy_qwen()` (`.qwen/commands/`).

**3. Auto-detection and `--pi` force flag follow the existing pattern**

Detection line `[[ -d "$TARGET/.pi" ]] && ENVS="${ENVS:+$ENVS }pi"` appended after the qwen line; `--pi` case branch setting `FORCE_ENV="pi"`; `pi) deploy_pi ;;` dispatch branch; `--pi` added to the "Valid options" and "Or force a target" messages. Rationale: consistent with how all four existing targets are wired.

**4. Spec strategy: add a new `pi-deploy` capability, no modified capabilities**

The repo's practice is that a deploy target introduced through the OpenSpec workflow gets its own spec capability (`qwen-deploy` is the precedent). `pi-deploy` mirrors the `qwen-deploy` requirement structure (auto-detection, force flag, commands as-is, skills unchanged, progress output) with pi's paths. No existing spec's requirements change.

**5. `.gitignore`: add `.pi/`**

All four existing deploy targets are gitignored in this repo. The repo's own `.pi/` is untracked derived content (core files from `openspec init` plus, after this change, deployed audit commands/skills) — `./deploy.sh .` merges into it exactly like `.opencode/`. Ignoring it stops accidental commits of derived content; no tracked files are affected.

**6. Error-message init hint: `openspec init --tools pi → creates .pi/`**

The "Initialize one of" block in deploy.sh's error path tells users how to create each target directory. The pi hint uses `openspec init --tools pi` per task 1.4, distinguishing pi from the bare `openspec init` hints for opencode/qwen.

## Risks / Trade-offs

- [Filename collision in `.pi/prompts/`] → Deployed names (`opsx-apply-audit`, `opsx-audit`, `opsx-security-audit`, `opsx-validate`) are disjoint from this repo's core prompts (`opsx-apply`, `opsx-archive`, `opsx-explore`, `opsx-propose`, `opsx-sync`), so nothing is overwritten here. In any project, a same-named user prompt would be overwritten — same behavior as all existing targets (deploy.sh never backs up or merges).
- [pi format drift] → If pi changes its prompt-template or skill frontmatter requirements, the as-is copy could produce files pi rejects. Mitigation: verified against pi 1.1.0 docs; any future content change to `commands/*.md` or `skills/*/` is tracked as a separate change.
- [Stale deployed files] → deploy.sh never removes files from prior deployments for any target; pi follows the same behavior. Out of scope.
- [This repo's untracked `.pi/` becomes gitignored] → It was untracked before; ignoring it only stops accidental commits of derived content. No tracked files are affected.

## Migration Plan

1. Implement the deploy.sh additions, spec delta, test block, README, and .gitignore changes
2. Verify: `bash tests/deploy_test.sh` exits 0 (including the new pi block); `bash -n deploy.sh` passes; `./deploy.sh .` in this repo deploys the four source commands to `.pi/prompts/` and four source skills to `.pi/skills/` byte-identical, leaving the pre-existing core files untouched
3. Rollback: revert the commit — no data migration, no generated state to clean (deployed files can be deleted manually if needed)
