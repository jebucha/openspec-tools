## Context

deploy.sh supports four deploy targets (opencode, kiro, claude, gemini), each with a `deploy_<env>()` function, a force flag, a directory auto-detection line, and an error-message entry. Gemini is the only target requiring format conversion (markdown → TOML); the other three are plain copies with at most a rename or path split. See proposal.md for motivation.

The repo itself is a Qwen Code project: it contains a `.qwen/` directory generated by `openspec init` (core workflow commands/skills, `generatedBy: 1.9.0`), sitting alongside the gitignored `.opencode/`, `.kiro/`, and `.claude/` directories.

## Goals / Non-Goals

**Goals:**
- Make `qwen` a first-class deploy target with the same UX as the existing four (auto-detect, force flag, progress output)
- Remove gemini support completely from deploy.sh, specs, README, and .gitignore
- Keep the change minimal and mechanical — no restructuring of deploy.sh beyond the swap

**Non-Goals:**
- No changes to command/skill *content* (frontmatter, wording)
- No changes to how `openspec init` generates core workflow files for qwen
- No changes to `install.sh` (it copies only non-hidden entries, so deploy targets never flow through it)
- No restructuring of the per-target function pattern in deploy.sh

## Decisions

**1. `deploy_qwen()` copies as-is, mirroring `deploy_opencode()`**

Evidence: the repo's own `.qwen/commands/opsx-apply.md` and `.opencode/commands/opsx-apply.md` are the same format — plain markdown with YAML frontmatter (`name`, `description`) — and both use `.qwen/skills/<name>/SKILL.md` / `.opencode/skills/<name>/SKILL.md`. Filenames keep the `opsx-` prefix (no subdirectory split like claude, no TOML conversion like gemini).

Alternatives considered:
- Converting to some qwen-specific format — rejected; no such format exists in observed qwen projects
- Reusing `deploy_opencode()` with a parameter — rejected; the existing per-target function pattern is the repo convention, and a parameterized function would be a refactor beyond this change's scope

**2. Spec strategy: remove `gemini-deploy`, add `qwen-deploy` (symmetric swap)**

The repo's practice is that a target gets a spec capability when it was introduced through the OpenSpec workflow (only gemini has one; opencode/kiro/claude predate it). A symmetric swap keeps the spec surface honest: the capability being removed is removed, the capability being added is added.

Alternatives considered:
- Remove only, no new spec (qwen is "too trivial") — rejected; leaves the new detection/flag behavior undocumented in specs
- A general `deploy-targets` spec covering all four — rejected; bigger reframe than this change warrants, would require rewriting opencode/kiro/claude behavior that was never specced

**3. `.gitignore`: replace `.gemini/` with `.qwen/`**

All four existing deploy targets are gitignored in this repo; the repo's own untracked `.qwen/` is the only inconsistency. After this change, `./deploy.sh .` in this repo will merge audit commands/skills into the existing `.qwen/` (alongside `openspec init`'s core files), exactly like `.opencode/` — so it is derived content and belongs in .gitignore.

**4. Error-message init hint: `openspec init → creates .qwen/`**

The "Initialize one of" block in deploy.sh's error path tells users how to create each target directory. For qwen, `openspec init` is the real generator (proven by this repo's `.qwen/`), unlike claude/gemini which used bare `mkdir`.

**5. Explicit exclusion list (scope guard)**

- `gemini-pro` in audit-report filename examples (README "Audit Persistence" section, `openspec-audit-change/SKILL.md`, `openspec-validate-change/SKILL.md`) — these are *model* identifiers for multi-LLM audit comparison, not deploy targets. Untouched.
- `openspec/changes/archive/` — historical record, including the original `adapt-deploy-for-gemini` change. Untouched.

## Risks / Trade-offs

- [Existing `.gemini/` projects silently stop being detected] → The error message lists supported directories; `--qwen` is the replacement. Acceptable: the team has moved off Gemini CLI, and this is flagged **BREAKING** in the proposal.
- [Stale `.gemini/commands/opsx/*.toml` files left in old projects] → Out of scope; deploy.sh never cleans up prior deployments for any target (same behavior for all four existing targets).
- [Qwen Code command frontmatter differences] → Source commands carry a `description` frontmatter field, which qwen accepts (its own generated commands carry `name` + `description`). If qwen ever requires `name`, that is a content change to `commands/*.md`, tracked separately.
- [This repo's untracked `.qwen/` becomes gitignored] → It was untracked before; ignoring it only stops accidental commits of derived content. No tracked files are affected.

## Migration Plan

1. Implement the deploy.sh swap, spec deltas, README, and .gitignore changes
2. Verify: `./deploy.sh --qwen .` in this repo deploys into the existing `.qwen/`; `bash -n deploy.sh` passes; `openspec validate` passes
3. Rollback: revert the commit — no data migration, no generated state to clean
